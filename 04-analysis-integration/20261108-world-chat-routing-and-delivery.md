# 普通聊天、密語與隊伍聊天的 Server 契約

日期：2026-11-08。此為完整 Server 持續開發中的聊天增量，需求來源是使用者要求持續完成各功能。原件格式另見[REA 聊天與密語分析](20261108-native-chat-and-whisper.md)。下列路由、限流、收件期限與標籤是重建 Server 政策，不能當成原服規則。

## Client 收發

- C0E `kind:u8 + text:string8`：kind0 是普通聊天；kind2 是已有技能／普攻動作文字，不可轉為聊天或重複造成傷害。既有 `/party` 管理命令先行分流。
- C19 `kind:u8 + recipient:string8 + text:string8`：kind0 才是發話。普通角色名稱為密語；`!!` 是已由原件「組隊:」UI 與人數檢查補證的隊伍頻道；`!1`、`!2`、`!3` 是原生公會頻道入口，本輪尚未有公會權限，不轉成附近聊天。
- C19 kind1 是原生聊天忽略姓名的通知，不是玩家 authored text；本輪只解析並忽略，不能重新廣播。完整拒收／黑名單尚未實作，不能宣稱已支援。
- S0A type18（hex12）：`12 + byteLength:BEu16 + CP950 bytes`，無尾 NUL。已證此分支直接追加原生聊天歷史，不依賴遠端 actor，不走 type17 三秒替換提示。選用 type18 作三種重建聊天的共同顯示承載，不能說 type18 本身就是原版三頻道。
- 顯示文字為 `[附近] 真實角色名>內容`、`[隊伍] 真實角色名>內容`、`[密語] 真實角色名>內容`；密語發話者自看為 `[密語給實際角色名] 真實角色名>內容`。不以 self actorRef1 假裝另一個玩家發話。
- 拒絕發話使用已證 S0A type17 短訊息，回報無隊伍、對方不在線／載圖中、限流或佇列已滿。這是重建錯誤文案；不使用 S02 重建登入介面。

## 身份與投遞範圍

只能由當前已認證、已提交世界載入的精確租約（account／character／generation／connection）送出。署名從角色資料取出，封包無權提供 senderName、權限、partyId 或目標租約。收件人採提交當時的精確在線連線快照。

|頻道|提交時收件資格|取件時再次檢查|
|---|---|---|
|附近|相同 mapRef 及內容 revision，X、Y 各距離不超過8格，包含自己|雙方仍是原精確連線、已提交載圖、相同地圖版本且仍在兩軸半徑8內；發話者離線／換圖即捨棄延遲訊息|
|密語|以實際角色名正規化查詢單一在線、未 pending 載圖的對象，另給自己一次回顯|收件者仍是原連線；載圖中先不取件，可在期限內提交後再取，重登新連線不繼承|
|隊伍|當前隊伍所有已提交在線成員，包含自己，允許跨圖|發話者與收件者都仍屬原 partyId；退隊／解散後不送舊隊伍訊息|

附近範圍是17×17格候選矩形，不是「總寬8格」，也不承諾穿牆／遮擋原服規則。密語沒有離線信箱；離線時明確拒絕，不退化廣播。公會及其他未知頻道不授權發送。

## 有界保存與交易

文字必須可用嚴格 CP950 編碼，編碼後最多255 bytes；拒絕空白、控制字元及不可編碼字元。姓名取角色權威值，密語目的正規化只用於查找，回顯使用實際姓名。Server 顯示標籤與姓名加入後，S0A body 使用真正的 u16 位元組長度，不能套 string8 長度或 UTF16。

每個角色每10秒最多5次成功發話，跨重登保留。無效內容、離線目標、無隊伍、滿佇列不計成功額度。每個精確收件連線最多256筆 pending；任一收件人已滿則整筆發話拒絕，不能只送部分隊員仍回成功。每次最多取32筆，以提交序號排序。

訊息與操作收據期限2分鐘，送件／取件時清理過期資料及被新租約取代的佇列。每角色活操作收據上限256筆，達上限不逐出尚在期限內的既有收據。內部 operationId 在保留期限內相同 payload 重播回同一結果、不同 payload 拒絕；原生封包本身沒有提供此 operationId，不能誇稱可辨識玩家有意重複輸入的文字。期限過後不再保證識別同一內部操作。

發送在一個交易完成身份、名冊、範圍、限流、所有收件容量與佇列／收據寫入。鎖序是本人租約、隊伍 gate、聊天 gate，不拿其他人的連線鎖。取件同樣重驗資格後刪除已取訊息，為 **at-most-once dequeue**：取件交易提交後若程序或 TCP 寫入失敗，畫面可能漏顯，不承諾端到端 exactly-once 或已讀確認。聊天不改變 EXP、金錢、道具或戰鬥資源。

新增4類表為 chat gate／queue／operations／rate，World 輔助表檢查48→52。已有 SQLite 角色庫先一致備份再建缺表，不清空角色、物品、隊伍或金鑰。此短暫收件資料不是永久聊天紀錄，也不是供管理員查閱的稽核系統。

## 驗證與待完成

完整 .NET 回歸721項通過；其中本輪Store定向12項、Host wire流程2項。Store覆蓋範圍含邊界8格、雙方移圖／退隊、跨圖密語／隊聊、離線與pending載圖、精確租約替換、跨重登限流、2分鐘期限、重播衝突、排序、防重、競爭、容量、故障回滾與既有庫一次備份。Host覆蓋三頻道隔離、未知公會／kind1不廣播、kind2仍走動作、中文長訊息byte length及限流後仍能操作。

三名獨立合成客戶端的實際 TCP 共7項情境通過：附近AB／遠處C隔離、兩種指定收件密語、未知公會／kind1不廣播與單人無隊拒絕、退隊後排除、離線／不存在目標拒絕及新租約無重播、8次連續發話實際5成功／3限流且10.3秒後恢復、自己的Host重啟後無舊訊息並可再次發話。S0A18逐筆驗證BEu16、CP950 round-trip、無NUL及序號。最終Host DLL SHA256：`eac6004e4be43c861a98ae4c65029f9e8915be05e6911a66070b9aa9005af910`；這是測試成品識別，不公開私有實作。

以上不證明PostgreSQL執行期負載／併發或原生GUI。原生聊天歷史樣式、多 Client 的實際輸入操作、黑名單／拒收、公會聊天、好友／郵件及完整遠端玩家外觀仍需後續工作。不能因聊天可投遞就把整個 A-014 或多人場景標為完成。

後續原生驗收應一次測三名不同角色：附近對話僅同圖範圍內可見、選定角色密語只雙方可見、隊伍頻道只在線隊員可見，並測遠離／跨圖、退隊、中文長訊息與限流恢復。另確認連續訊息能保留在聊天歷史、沒有冒用 self actor 產生泡泡、離開重登不補舊訊息。GUI未測前只記待測，不將本輪合成客戶端結果套用為使用者實測。
