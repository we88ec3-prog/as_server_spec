## 管理與帳號流程契約（Server 設計）

- 沿用已啟動的本機 Server、持久資料庫、端口與管理金鑰；新增帳號不需要重新產生金鑰，也不能清除既有角色。
- 管理入口仍為 loopback `/admin-ui/`，受保護 API 仍使用 `X-Admin-Key`。本機捷徑從現有私有設定取出金鑰，先檢查服務及已知帳號的授權讀取，再由使用者執行時複製到剪貼簿並開管理頁。金鑰不加入 URL、命令列或公開文件。使用者貼上金鑰後按驗證。
- 新帳號經既有 `POST /admin/accounts` 建立；角色仍透過原生創角 C02／C04 流程。新帳號不等於預建角色。不得把 worlddemo 密碼、角色或管理權限複製給新帳號。
- 補充本機互動入口可隱藏輸入密碼，呼叫同一管理 API，產生帳號專屬的創角／登入捷徑。密碼不寫入捷徑；新建與既有帳號捷徑重建分開，後者不重設密碼。
- 該入口採 3–12 ASCII 英數與底線 ID，密碼依既有原生 UI 相容政策為 4–8 ASCII 英數。ID 上限是本機捷徑的保守設計限制，不能冒稱已證原服完整規則。帳號、角色與世界進度由各自持久身份隔離。
- Web 建帳後也可只產生既有帳號的捷徑；不再重複建帳。不自動停止使用者保留的 Client 或 Server。

## 能力窗：已證部分與待修正內容

原件 SHA256 `db3df616f68b9f32163abc4b88de9d310562b2ddfe955aaa5ba7fcff729e1145`，Ghidra 12.1.4：

1. `0x540050` 刷新狀態 UI 時，child 0x19 由自身外觀職業碼及本地字串 0x1c7+code 顯示職業；child 0x1a 則讀 Status+0x210 的獨立文字。兩欄不是同一來源，不得僅因預言者文字直接改 Mage 職業碼。
2. `0x53f8a0` 接收 S08，0x40 區塊填入等級、四種最大資源、能力與聲望相關欄；0x20 更新四種目前資源；0x10 更新經驗相關欄；0x08 的 string8 轉為 Status+0x210 文字。完整 wire 順序見 [A-008](../task_a/roy2/A-008-analysis.md)。
3. UI 映射：Status+0x41c 為等級；+0x420/+0x428/+0x430/+0x438 對應 HP/MP/SP/BP 上限，+0x478/+0x47c/+0x498/+0x480 為目前值；+0x452/+0x458/+0x460 為三個 signed-byte 聲望值，+0x454/+0x45c/+0x464 為相應經驗；+0x468 為控制加點按鈕顯示的餘點。這些是 Client 顯示映射，不是原服出生或成長公式。
4. `0x53f510` 建構子只初始化部分欄位。截圖的 -858993460 等於 signed 0xCCCCCCCC，與未填入資料一致；它本身不能證明是哪條程式路徑造成滑過時卡死。
5. 目前 Server World 提交路徑沒有發出 S08 完整初始化。這是已確認的缺口；不得把外觀 S33 當作完整角色狀態。
6. 另有待查 metadata 路徑：`0x4cebc0` 在 metadata 資料指標為零時回傳失敗，不設已載入旗標；必須確認能力窗 hover 是否走到此路徑，不能先宣稱它是本次當機原因。

後續實作應使用 Server 權威且一致的初始／持久狀態發 S08，明確標註出生數值政策與原版未知公式；追出稱號及 hover 資料依賴，避免只改顯示文字掩蓋缺口。驗收需包含新帳號創角、舊角色重登、五職業狀態窗、滑過職業／稱號／能力與正常退出。目前尚未修復或完成此驗收。
