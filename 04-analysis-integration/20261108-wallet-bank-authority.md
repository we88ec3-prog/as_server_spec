# 錢包與銀行存提款的Server權威契約

日期：2026-11-08。關聯：[A-013經濟分析](A-013-economy-contract.md)、[原生封包分析](../03-analysis-requests/A-013-roy1-economy-wire.md)。本頁補持久資金與交易安全規則，讓其他開發者能獨立實作；不包含私有程式碼或使用者資料。

## 來源與範圍

使用者要求繼續開發後續遊戲功能；本輪為銀行NPC服務準備錢包／銀行資金能力。A-013已區分Merchant、Exchange與Trade封包，並要求Server決定價格、資產原子性、防重與溢位；它沒有證明原服金額上限、銀行手續費或完整銀行操作。因此下述初始值、上限、零手續費與資料結構都是**重建設計**，不是原版規則。

本輪只處理每角色錢包與銀行貨幣，不代表銀行物品倉庫、玩家交易、商店價格或原生銀行畫面已完成。NPC距離、服務能力、對話context、原生回覆欄位與畫面投影由對應Host／原生UI契約補充。

## 狀態與金額

每角色持久保存character ID、wallet balance、bank balance、共同revision及policy revision。明示政策`development-economy-v1`：

| 項目 | 本輪重建值 |
| --- | --- |
| 新角色錢包／銀行 | 0／0 |
| 每個餘額上限 | 1,000,000,000 |
| 單次金額 | 整數1至1,000,000,000 |
| 存／提款手續費 | 0 |
| 每次成功交易 | 共同revision增加1 |
| 業務拒絕 | 餘額及revision不變 |

讀取只建立零餘額狀態，不給測試金錢、不從Client快取回填。測試資金或遊戲獎勵必須由可信Server事件發放至錢包，有固定event ID及收據；正常世界沒有因讀取或重登免費增加資金。若隔離Development測試需要1000金，應以獨立固定事件發放一次，而非在讀取函式中補成1000。

不得依原生u32欄寬宣稱原服最大金額為2³²−1。Client可提供合法存提款數量意圖，但不能提供可信價格、目標餘額、要扣誰的錢或獎勵金額。

## 原子存提款與拒絕

存款必須確認wallet≥amount、bank有足夠餘裕，然後同一交易wallet減amount、bank加amount。提款反向進行。零手續費時兩邊合計守恆；可信獎勵才會增加總額。

檢查金額範圍、身份、目前owner lease、已提交載圖及revision CAS後才變更。資金不足回`InsufficientFunds`；目的餘額會超限回`BalanceLimit`。兩者為業務拒絕，不能變更資金、不能因失敗直接斷線；不得先扣一邊或先回成功。上限判斷用可用餘裕與amount比較，避免先相加造成溢位。

非正整數、超範圍金額或不合法operation ID屬輸入拒絕；舊revision、錯owner、舊generation／connection、尚在載圖或已斷線屬權威衝突。這些都不能留下成功資產變更。revision已達最大值則拒絕增加，不能繞回負值。

## 收據、並行與審計

一筆交易包含兩個餘額、revision與審計收據；任一寫入失敗，全部回滾。審計至少保存角色、operation ID、意圖kind、amount、交易前後wallet／bank、結果及時間；拒絕也有收據，前後餘額相同。

同角色相同operation ID與相同kind／amount／policy只回原始收據，不再次扣款或加款。重用ID但內容不同為衝突。同時提交同一事件只成功一筆；兩個不同操作爭同一revision只允許一筆，另一筆重讀後建立新意圖。

重放回傳的State可能是歷史snapshot，**不能寫回資料庫，也不能直接投影為目前餘額**。Host處理重送或拒絕後重讀權威狀態，尤其原生UI若已樂觀修改顯示值，應用真實快照校正。拒絕收據亦固定其原結果；狀態改變後要執行新的存提款，使用新operation ID。

原生動作沒有全球唯一nonce時，Server收據不能自行辨認所有相同網路封包是否為同一意圖。Host需以有效NPC／對話context、one-shot提交及版本CAS產生可信內部操作ID，不能把每次重送換新ID後宣稱已達exactly-once。Server發肯定成功與資源畫面更新須在資料庫提交後。

## 初始化與驗證

採新增資金狀態表與操作審計表；既有角色、技能、能力、背包、地圖及進度不重置。檔案型SQLite在已有人物／帳號且缺少新增表時，沿既有一致備份流程先產`pre-world-v6`備份，再做additive schema。下一次初始化表已齊全，不應再因同一新增內容重複備份。政策變更應明示新版本及遷移，不偷偷改相同版本的上限。

本輪定向驗證：Domain7項、SQLite Store7項全部通過。涵蓋零讀取不grant、可信獎勵、防重與不同意圖碰撞、存提款守恆、資金不足與目的餘額上限、非法金額、revision耗盡、錯owner／未提交載圖／舊lease／斷線、並行同事件與同CAS、防止歷史收據覆寫、故意令收據失敗時雙餘額與版本回滾，以及既有進度新增表備份一次且完整保留。

這不是全套Server回歸、PostgreSQL實測或原生Client銀行GUI驗收；後續需集中確認NPC開銀行、存提款後畫面、失敗校正、關窗／重送、重登與Server重啟餘額保留。
